## The Real Decision You Need to Make (MVP-Level)

You must choose **one of these two operational models** for MVP:

---

## OPTION 1 — Single Deployment, Multi-Society (Recommended for Real Users)

### What this means

* One backend
* One database
* Many societies in the `societies` collection
* Every query is scoped by `societyId`

### How it works

* Onboarding flow:

  * Create Society
  * Create first Admin User linked to that Society
* Every domain object includes:

  * `societyId`
* Authorization checks always include:

  * `req.user.societyId === resource.societyId`

### Why this is MVP-safe

* No schema refactor required
* No breaking change later
* Matches real-world usage immediately
* Supports:

  * Society A today
  * Society B tomorrow
  * Society C next month

### What you must be strict about

* **Every query must be society-scoped**
* No “global” reads
* No cross-society joins
* No admin that can see multiple societies (in MVP)

### Mental model

> **Single codebase, single DB, multiple isolated tenants**

This is how most serious SaaS MVPs actually launch.

---

## OPTION 2 — One Deployment per Society (Operationally Simple, Commercially Slower)

### What this means

* Separate backend per society
* Separate database per society
* Society table often has exactly one record

### Why people choose this

* Very simple authorization
* Minimal risk of data leakage
* Easier early ops if you onboard one society at a time

### Why it becomes a problem

* Operationally heavy
* Hard to sell to multiple societies quickly
* Migration to multi-tenant later is painful
* CI/CD, infra, monitoring multiply fast

This option only makes sense if:

* You are serving **1–2 pilot societies** only
* You want zero infra complexity short-term
