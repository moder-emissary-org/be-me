System-Level Architecture Update and Society-Level Strategy Report <br>
Apartment & Society Management SaaS – Consolidated Direction <br>

1. **Executive Context**

The product is moving from a single-tenant installation mindset to a public SaaS onboarding model due to extreme budget constraints and a goal of open online adoption. The system must support multiple societies registering independently through one hosted frontend and one shared backend. <br>

The updated architectural direction is: <br>

Single hosted backend <br>
Single MongoDB Atlas cluster <br>
Multi-tenant logical isolation <br>
Multiple Society documents allowed <br>
Strict societyId enforcement across the entire system <br>

This replaces the earlier “system-level singleton” model. <br>

---

2. **Deployment Model Clarification**

Previous Direction (Rejected for SaaS Goal) <br>

Single deployment <br>
Single database <br>
Exactly one Society document <br>
Bootstrap blocked after first creation <br>

This model works only for per-client installations. It does not support public onboarding from multiple admins within one hosted application. <br>

New Direction (Approved) <br>

Single backend deployment <br>
Single MongoDB cluster <br>
Multiple societies allowed <br>
Each society is a tenant container <br>
Each society has its own admin and related users <br>

This is true multi-tenant SaaS. <br>

---

3. **Multi-Tenant System Model**

Each Society acts as a tenant boundary. <br>

Structural hierarchy remains: <br>

Society <br>
→ Apartment <br>
→ User <br>
→ Complaint <br>
→ Visitor <br>
→ Notice <br>

Every document except Society must contain: <br>

societyId <br>

Isolation rule: <br>

A user can only access data where: <br>
resource.societyId === authenticatedUser.societyId <br>

This is enforced in the service layer. <br>

No controller-level trust. <br>
No client-provided societyId trust. <br>
SocietyId is always derived from authenticated backend user resolution. <br>

---

4. **Database-Level Design Decision**

System-Level Singleton (Removed) <br>

Do not enforce a constant unique field (e.g., isSystemRoot). <br>
Do not block creation after first society. <br>
Do not use name uniqueness to simulate singleton. <br>

Society-Level Authority Model (Adopted) <br>

Each bootstrap operation: <br>

Creates one Society <br>
Creates one Admin user linked to that society <br>

There is no global limit on number of societies. <br>

Each society is logically independent inside the shared database. <br>

---

5. **Tenant Isolation Enforcement Rules**

Mandatory architectural invariant: <br>

No repository query is allowed without societyId scoping. <br>

Examples: <br>

Incorrect:
findById(id)

Correct:
findOne({ _id: id, societyId })

Incorrect:
update({ _id })

Correct:
update({ _id, societyId })

This prevents cross-tenant data access. <br>

Authorization enforcement lives in: <br>

Service layer only <br>
Never in controllers <br>
Never assumed from client <br>

Controllers remain orchestration-only. <br>

---

6. **Infrastructure Model**

Single MongoDB Atlas Cluster <br>

The system will use: <br>

One managed MongoDB Atlas cluster <br>
Replica set (default high availability) <br>
Vertical scaling as load increases <br>

Replica sets provide: <br>

Primary node <br>
Secondary nodes <br>
Automatic failover <br>

Sharding is not required for MVP and early growth. <br>

Sharding is only considered when: <br>

Data size becomes very large <br>
Write throughput exceeds replica set capability <br>
Vertical scaling is insufficient <br>

For early-stage SaaS with text-heavy operational data, a single replica-set cluster is more than sufficient. <br>

---

7. **Budget-Conscious Architecture**

Why this model is optimal for constraints: <br>

No per-society deployment overhead <br>
No per-society database cost <br>
No infrastructure duplication <br>
Simple scaling path (upgrade cluster tier) <br>
Operational simplicity <br>

Growth path: <br>

M0 → M10 → higher tiers <br>
No architectural rewrite required <br>

The architecture scales vertically first, then horizontally only when truly necessary. <br>

---

8. **Product-Level Implications**

Public onboarding flow: <br>

Admin visits website <br>
Registers society <br>
Backend creates Society + Admin <br>
Society becomes new tenant <br>

Multiple societies coexist safely in same database. <br>

There is: <br>

No super admin (MVP scope) <br>
No cross-society dashboard <br>
No shared data between societies <br>

Each society behaves like a self-contained container within the shared system. <br>

---

9. **Strategic Positioning**

This model achieves: <br>

Budget efficiency <br>
Public SaaS onboarding <br>
Clear tenant isolation <br>
Minimal infrastructure complexity <br>
Future scalability <br>

It aligns with: <br>

Authority-first design <br>
Society as root tenant boundary <br>
Backend-owned authorization <br>
Strict service-layer enforcement <br>

---

10. **Final Architectural Position**

The system is now defined as: <br>

A multi-tenant SaaS platform <br>
Using logical tenant isolation <br>
With Society as the tenant key <br>
Deployed on a single MongoDB Atlas cluster <br>
Enforcing strict societyId-based authorization in services <br>

Global singleton enforcement is removed. <br>
Tenant-level isolation becomes the primary invariant. <br>

This direction is consistent with growth, budget, and MVP scope. <br>
